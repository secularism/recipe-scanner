# v1.2 研究：功能

**Milestone:** v1.2 用户身份与远程同步  
**日期:** 2026-06-27

## 基础能力

### 用户身份

- 用户可在小程序内通过 `uni.login` 静默登录。
- 后端用一次性 code 调微信 `code2Session`。
- 后端按微信 openid 建立或更新 `User`，有 unionid 时一并保存。
- 后端返回应用自己的 session token，而不是微信 `session_key`。
- 小程序本地保存应用 token，并在受保护同步接口中携带。
- 登录失败时，小程序继续保持本地可用。

### 收藏同步

- 用户登录后，已有本地收藏 id 不丢失。
- 首次登录合并会上传本地收藏 id，并按用户和菜谱 upsert 远程收藏。
- 收藏页可从远程恢复收藏。
- 收藏/取消收藏保持本地优先：UI 先更新本地，再尝试远程 mutation。
- 远程失败不会删除本地收藏 id。
- 失败的收藏同步有可重试路径。

### 历史同步

- 用户登录后，已有本地历史记录不丢失。
- 首次登录合并会上传本地历史。
- 服务端用稳定的 client item id 或确定性签名避免重复合并。
- 结果页生成历史后，已登录用户可写入远程。
- 历史页可从远程恢复记录。
- 删除和清空历史要么同步到远程，要么在远程失败时保持明确的本地 pending 状态。

### 同步状态与恢复

- 小程序记录当前用户是否已经完成首次合并。
- 本地缓存仍是快速展示来源。
- 远程拉取可以 hydrate 本地 store，但不能无脑覆盖未同步的本地变更。
- 同步失败后可以重试，且不丢数据。

### 安全与隐私

- appSecret 只存在后端。
- 微信 `session_key` 只存在后端。
- 受保护 endpoint 必须要求 bearer session token。
- v1.2 不需要用户授权昵称头像，因为静默身份足够支撑同步。
- 后端只保存同步所需的最小身份数据：openid/unionid、时间戳等；昵称/头像留给后续资料页。

## 值得保留的体验差异

- 应用应继续有离线容忍度：远程失败时，收藏和历史仍能在本机工作。
- 首次登录合并应该是增量、保护性操作，而不是让用户担心旧数据被覆盖。
- 用户不需要理解账号细节；登录尽量无感，失败时才给可恢复提示。
- 本地 matcher/generator 继续快速、稳定、独立于账号状态。

## 延后能力

- 用户资料页、头像、昵称编辑。
- 跨设备冲突 UI。
- 完整离线操作队列和逐项冲突解决。
- 识别任务、上传、对象存储、OCR 和图片工作流。
- AI 生成菜谱。
- 管理后台或用户管理后台。
- HTTPS、request 合法域名、ICP、隐私指引等正式发布清单，除非后续明确把发布准备纳入 v1.2。

## 复杂度评估

| 功能 | 复杂度 | 原因 |
|---|---:|---|
| 微信静默登录 | 中 | 涉及外部 `code2Session`、env secret、服务端自定义 session。 |
| Auth guard/session 表 | 中 | 必须避免泄露 `session_key`，并处理过期、无效 token。 |
| 收藏合并 | 低到中 | 现有 schema 已有 user/recipe 唯一约束。 |
| 历史合并 | 中 | 需要幂等字段或签名，避免重试上传导致重复历史。 |
| 本地优先同步 store | 中 | 要保留当前本地体验，同时增加远程重试状态。 |
| 跨设备冲突解决 | 高 | 建议延后，v1.2 只做增量合并和简单最后本地操作优先。 |
